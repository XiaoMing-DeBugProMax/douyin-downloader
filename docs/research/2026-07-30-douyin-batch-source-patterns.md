# 抖音批量来源交互模式调研

日期：2026-07-30

## 研究问题

同类 GitHub 项目如何组织作者主页、合集和多链接批量下载？本项目首期应只允许一次提交一个来源，还是允许一次提交多个来源？

本记录只采用项目自身 README、配置示例和源代码等一手资料。这里的“多来源”专指多个作者主页或多个合集，不等同于多条单视频链接。

## 项目对比

### jiji262/douyin-downloader

- 支持单作品、作者主页、合集、音乐等链接；作者主页还可通过 `post`、`like`、`mix`、`music` 等模式展开不同作品集合。
- `config.example.yml` 将 `link` 定义为列表；命令行的 `--url` 也使用可重复追加参数，因此能够在一次运行中接收多个链接。
- 调用层从配置读取全部链接后按顺序逐个执行。每个链接独立解析、下载、记录历史和产生结果，最后才汇总全部链接的成功、失败与跳过数量。
- 这意味着它支持“多来源一次提交”，但没有抹掉来源边界；更接近“一个运行会话包含多个来源作业”，而不是“所有来源混成一个批次”。
- SQLite 去重以作品为核心；同一作品从不同模式或来源被发现时可避免重复下载。

### Johnserf-Seed/f2

- Douyin 能力覆盖主页作品、公开合集作品、点赞作品、收藏夹作品等，并区分公开访问与需要登录的能力。
- 主页处理器从当前 `url` 提取一个 `sec_user_id`，随后分页展开该作者作品；合集处理器从当前 `url` 提取一个 `mix_id`，随后分页展开该合集作品。
- 工具层存在“从文本提取多个用户 ID / 多个合集 ID”的辅助能力，但主处理器仍以一个来源 ID 为一次处理上下文。由此可见，“能解析多个 ID”与“把多个来源合并成一个任务”是两层不同的能力。
- 该结构支持我们把来源扫描抽象成统一接口，同时保留每个来源独立的游标、授权状态、错误和扫描结果。

### TikHub/TikHub-Multi-Functional-Downloader

- GUI 明确拆分“单视频下载”“用户主页视频”和“批量下载”。
- “用户主页视频”一次输入一个主页，先取用户资料与作品列表，再让用户选择作品或全部下载。
- 它的“批量下载”是每行一条单视频链接，也可从文本文件导入；这不是多个主页或多个合集的来源扫描。
- 这种拆分说明产品界面需要明确区分“多个已知作品链接”与“一个来源展开多个作品”，否则用户会把两种批量概念混在一起。

## 共同模式

1. **来源类型决定扫描器**：作者主页、合集、收藏夹等拥有不同分页、授权和失败语义，不能只当作普通 URL 列表。
2. **作品是最终去重单位**：多个来源可以发现同一作品，下载与档案层应按作品 ID 去重。
3. **来源边界需要保留**：成熟实现即使接受多个 URL，也会逐个处理并保留各自结果，而不是共享一个无法定位问题的扫描状态。
4. **多单视频链接是另一项能力**：它适合用户已经拥有作品清单的场景，不能替代主页或合集的自动发现；本项目首期没有必要把它放进“批量下载”的核心流程。

## 对本项目的建议

首期批量下载工作区可以允许用户一次添加多个公开来源，但应采用“来源清单”而不是无结构的大文本框：

- 每一项只能是一个作者主页或一个公开视频合集。
- 应用先逐项识别来源类型，并为每个来源单独扫描、显示范围、状态、作品数、授权要求和错误。
- 用户可以在预览阶段统一确认，但系统内部创建一个“批量操作”，其下包含多个独立“来源扫描/来源批次”；每个来源再产生作品任务。
- 跨来源按作品 ID 全局去重，并在预览中说明作品首次由哪个来源发现、还出现在哪些来源。
- 单个来源扫描失败不阻断其他来源；重试、取消和重新扫描可以精确到来源。
- 首期设置一个较小的来源数量上限，建议最多 10 个，避免风险控制、资源估算和用户误操作失控。
- 多条单视频链接导入可作为以后独立的输入方式，不应与主页/合集来源清单混为一个交互。

## 结论

不建议把产品限制为“每次只能提交一个来源”，也不建议把多个来源合并成一个没有内部边界的大批次。更合适的模型是：

> 一次批量操作可以包含多个来源；每个来源独立扫描和汇报，作品跨来源统一去重。

这既吸收了 `jiji262/douyin-downloader` 的多 URL 能力，也保留了 `f2` 的单来源处理边界，并避免把 TikHub 式“多条单视频链接”误当成来源批量下载。
